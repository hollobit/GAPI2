홈 대시보드 이용 절차 스코어카드 생태계 가이드라인 ID 계산기 도움말 2026-04 기준선 ↗

도움말 — 이 대시보드를 읽는 법

스코어카드가 의미하는 바, 왜 이 문제들을 해결해야 하는지, AI/Agent 준비도 18개 지표의 뜻과 측정 방법을 설명합니다.

1. 대시보드의 구조 — 3개 층위

  • Layer 1 · 문제 개선 스코어카드 — 2026-04 기준선이 지적한 7대 구조 문제가 지금 얼마나 해결됐는지. 카드의 배지(개선/부분/미개선)는 전수 215개 관점의 롤업이며, 대표 포털만 개선된 경우 "부분"으로 표기합니다(예: 항상 200 문제는 게이트웨이 8/172만 개선 → 부분).
  • Layer 2 · 등급 이동 — 포털별 사용자중심성(UF)·AI적합성(AI) 합산 점수의 2026-04→2026-08 이동. 점선+"부분측정" 배지는 일부 지표가 측정불가라 잠정치라는 뜻이며, 하락이 실제 퇴보가 아니라 미측정 때문일 수 있음을 나타냅니다.
  • Layer 3 · AI/Agent 준비도 히트맵 — 215개 포털 × 18개 지표. 셀 색은 0(빨강)~2(초록), 회색은 측정불가. 행 클릭 시 지표별 판정·측정방식·증거 링크가 펼쳐집니다.

2. 7대 문제 — 무엇이고, 왜 해결해야 하나

3. AI/Agent 준비도 18개 지표 — 의미·점수 기준·측정 방법

두 개의 합산 점수 — UF와 AI는 무엇을 재는가

  • 사용자중심성 UF (0~14점) — 사람 개발자가 겪는 마찰의 총량. 가입 용이성 → 승인 속도 → 기본 포맷 → 문서 품질 → 호출 한도 → 오류 처리 → SDK·샘플, 즉 "가입부터 첫 성공 호출까지"의 7단계를 각 0~2점으로 평가해 합산합니다. 한국 전수 평균 5.74(D).
  • AI 적합성 AI (0~14점) — 기계(에이전트)가 자율적으로 쓸 수 있는가. 기계가독 스키마 → HTTP 상태코드 → JSON 네이티브 → 오류 자기설명 → 프로그램 인증 → 한도 투명성 → CORS·HTTPS, 즉 "사람의 도움 없이 발견·호출·복구"가 가능한 7가지 전제를 평가합니다. 한국 전수 평균 2.35(E) — UF보다 낮은 이유는 사람용 우회로(전화·게시판·HWP 열람)가 기계에겐 없기 때문입니다.
  • 평가 방법 — 지표당 0(없음/비표준)·1(부분)·2(표준 충족)의 3단 척도로 채점 후 단순 합산합니다. 측정불가 지표는 0점 처리하지 않고 합산·분모에서 제외하며, 7개 중 일부만 측정된 포털은 "부분측정 (n/7)" 배지로 잠정치임을 표시합니다. 등급 구간: A(12~14) B(9~11) C(6~8) D(3~5) E(0~2). †표시 4개(도구 네이티브·llms.txt·데이터 제품화·통합 계정)는 2026-08 신설 실험 지표로 합산에서 제외하고 별도 추적합니다.
  • Before→After 비교 — 2026-04 기준선(문서·구성 조사)과 2026-08 재측정을 같은 지표 체계로 대조합니다. 측정 방식이 다른 지표(문서→실측)는 판정 주석에 명시해 "측정 교정"과 "실제 변화"를 구분합니다.

5. 지표별 개선 가이드 — 무엇을 어떻게 바꾸나

API 제공 기관 실무자를 위한 처방입니다. 대부분은 게이트웨이 설정 또는 반나절 작업 수준이며, 예제는 그대로 응용할 수 있는 형태로 실었습니다. 각 지표 표의 "개선 →" 링크와 연결됩니다.

HTTP 상태코드 http_semantics

게이트웨이/컨트롤러에서 오류를 상태코드로 매핑하세요. 백엔드 수정 없이 게이트웨이 응답 변환만으로도 가능합니다(data.go.kr이 실제로 이 방식으로 개선).

# 잘못된 키 → 401, 없는 자원 → 404, 파라미터 오류 → 400
HTTP/1.1 401 Unauthorized
Content-Type: application/problem+json

{"type":"/errors/invalid-key","title":"등록되지 않은 인증키","status":401}

JSON 네이티브 json_native

기본 응답을 JSON으로 바꾸고 XML은 &type=xml 옵션으로 유지하세요. 기존 이용자 호환을 위해 6개월 병행 공지 후 기본값을 전환하는 방식이 안전합니다.

GET /api/forecast?region=서울          → JSON (기본)
GET /api/forecast?region=서울&type=xml → XML (호환)

오류 자기설명 error_self_desc

RFC 7807(application/problem+json)을 채택하세요. 오류 코드표 HWP 대신 응답 자체가 원인·해결책을 설명하게 합니다.

{"type":"https://api.example.go.kr/errors/quota",
 "title":"일일 호출 한도 초과","status":429,
 "detail":"한도 1000회를 초과했습니다. 09:00(KST)에 초기화됩니다.",
 "instance":"/req/12345"}

기계가독 스키마 machine_schema

기존 문서를 OpenAPI 3.x YAML로 옮기고 /openapi.json 관용 경로에 게시하세요. Swagger Editor로 시작하면 반나절 작업입니다. 신규 API는 스펙 우선(spec-first)으로.

# https://api.example.go.kr/openapi.json 에 게시
openapi: 3.0.3
info: {title: 단기예보 조회, version: 2.0.0}
paths:
  /getVilageFcst:
    get:
      parameters: [{name: nx, in: query, required: true, schema: {type: integer}}]

프로그램 인증 programmatic_auth

키를 URL 쿼리에서 Authorization 헤더로 이전하세요. 로그·Referer 유출이 사라지고 표준 클라이언트와 호환됩니다. 쿼리 방식은 유예기간 병행.

# 이전: GET /api?serviceKey=abc123  (로그에 평문 잔존)
# 이후:
GET /api HTTP/1.1
Authorization: Bearer abc123

한도 투명성 rate_limit_transparency

IETF RateLimit 헤더 3종을 게이트웨이에서 부착하세요. Kong/nginx 플러그인 설정 수준의 작업입니다.

HTTP/1.1 200 OK
RateLimit-Limit: 1000
RateLimit-Remaining: 847
RateLimit-Reset: 3600

CORS·HTTPS cors_https

공개 데이터 API라면 CORS를 전면 허용해도 안전합니다(인증은 헤더 키가 담당). 게이트웨이 한 줄 설정입니다.

# nginx
add_header Access-Control-Allow-Origin *;
add_header Access-Control-Allow-Headers Authorization;

가입 용이성 signup_ease

조회성 API는 이메일 가입만으로, 저위험 API는 무가입 공용 샌드박스 키로 여세요. 본인인증은 개인정보 취급 API로 한정.

위험도 3단계 정책 예:
  공개 통계·날씨  → 가입 불요(샌드박스 키)
  일반 조회      → 이메일 인증
  개인정보 연계  → 본인인증 유지

승인 속도 approval_speed

자동승인 기준(개인정보 무관·출처표시·쿼터 준수)을 공개하고 충족 시 즉시 발급하세요. 심의는 예외로, 사유·기한을 명시.

활용신청 → 기준 자동판정(1초) → 즉시 키 발급
         → 기준 미충족 시에만 심의(사유+최대 3일 기한 고지)

기본 포맷 data_format

json_native와 동일 — 신규 API는 JSON 전용으로 시작하고, 파일 중심 포털은 최소한 카탈로그·메타데이터를 JSON API로 제공하세요.

GET /catalog/datasets?page=1  → {"datasets":[...], "total": 451}

문서 품질 doc_quality

HWP 첨부를 Swagger UI(OpenAPI 스펙 렌더)로 대체하세요. 스펙(machine_schema)을 만들면 문서는 자동 생성됩니다 — 한 작업으로 두 지표 개선.

docs.example.go.kr → Swagger UI로 스펙 렌더
+ '지금 실행해보기(Try it out)' 버튼 = 샘플 코드 불필요

호출 한도 rate_limit

기본 한도를 실서비스 가능 수준(일 1만+)으로 올리고, 증량은 신청 즉시 자동 처리하세요. 남용은 한도가 아닌 RateLimit 헤더+429로 제어.

기본 10,000/일 → 초과 시 429 + Retry-After → 증량 신청 API로 즉시 상향

오류 처리 error_handling

오류 응답을 단일 스키마로 통일하고 전 API에 강제하세요(게이트웨이 응답 검증). error_self_desc의 RFC 7807 채택이 곧 해법입니다.

모든 오류 = problem+json 단일 스키마
게이트웨이에서 스키마 위반 응답을 감지해 변환/경고

SDK·샘플 sdk_samples

openapi-generator generate -i openapi.json -g python -o sdk-python

4. 측정 방법론 — 판정을 신뢰할 수 있는 이유

  • 측정 방식 3계층 — live 실제 HTTP 호출(잘못된 키를 일부러 넣어 상태코드 정직성을 검증하는 식. 실키는 절대 노출하지 않고 더미 키 사용) · browser 실브라우저 렌더 관측 · doc 공식 문서·구성 기반. 상세 패널의 "측정방식" 배지로 구분됩니다.
  • 측정불가는 0점이 아닙니다 — 인증키 부재 등으로 검증 못 한 지표는 평균 분모에서 제외해 점수를 인위적으로 누르지 않습니다.
  • 판정 규칙 — 개선(점수 상승) / 유지(만점 유지) / 미개선(변화 없음) / 후퇴(하락) / 신규(2026-04 기준값 없음) / 측정불가. "후퇴" 다수는 문서 기반 낙관치가 실측으로 교정된 효과일 수 있어 별도 주석을 답니다.
  • 오탐 교정 의무 — 자동 탐지 결과는 표본 수동 재검증을 거칩니다(실사례: llms.txt 자동 탐지 3건이 전부 HTML 오류 페이지로 확인돼 교정, 교정 이력 공개).
  • 재현 가능성 — 모든 live 판정에 재현 curl 명령과 응답 샘플이 증거로 링크되며, serviceKey는 게시 전 마스킹됩니다.
  • 전체 정본 명세는 루브릭 명세 v1.0(저장소 output/expert_review_2026-08.md 부록 A) 참조.
