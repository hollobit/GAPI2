기계 발견성·자기설명 (Machine Discovery & Self-description)

에이전트는 사람이 읽는 HWP/웹페이지를 파싱할 수 없다 — 기계판독 스키마와 진입점이 있어야 API를 스스로 발견·이해·호출할 수 있다.

data.go.kr 현재: Level 0 — 기계판독 명세 전무. 문서가 HWP/PDF/HTML 산문뿐이라 에이전트가 엔드포인트·파라미터를 추론할 수 없다.

구조화 포맷 (Structured Format)

JSON은 LLM이 바로 파싱·생성하는 네이티브 구조다. XML 기본값은 토큰을 약 2.5배 소모하고 게이트웨이 오류 시 강제 XML로 되돌아가 에이전트 파이프라인을 깨뜨린다.

data.go.kr 현재: Level 1 — JSON을 지원하나 기본값은 XML이라 ?type=json 등 명시가 필요하고, 일부 경로에서 여전히 XML을 반환한다.

🇺🇸 18F 표준: "Support JSON and only JSON" — JSON 전용 응답 원칙🇬🇧 GDS: JSON 응답 표준화, XML은 레거시 상호운용 예외적 허용만

정직한 HTTP (Honest HTTP)

에이전트는 HTTP 상태코드로 성공/실패를 자동 분기하고 재시도·백오프한다. 오류에 200을 반환하면 표준 HTTP 클라이언트(requests·axios·fetch)가 모두 무력화되고 무한 재호출·잘못된 성공 판정이 발생한다.

data.go.kr 현재: Level 1 — 일부 오류에 상태코드를 쓰지만 불완전·비일관적(예: 500만 있고 401/404/429 없음)이다.

🇬🇧 GDS: 표준 상태코드(400/401/403/404/409/429/500) 사용 필수 + RFC 7807 권장🇦🇺 NAPIDS: 표준 HTTP 상태코드 사용을 전 API에 필수화
레퍼런스
  • RFC 9457 — Problem Details for HTTP APIs (obsoletes RFC 7807)
  • RFC 9110 — HTTP Semantics (status codes)
  • UK GDS API Technical and Data Standards
  • 한국 공공 API 개선 로드맵 §1.2 HTTP 상태코드 정상화 (gapi)

에이전트 인증 (Agent Authentication)

자율 에이전트는 서버 간(machine-to-machine) 무인 실행이 기본이다. URL 쿼리에 노출되고 2년마다 수동 갱신하는 API Key는 로그 유출과 운영 중 서비스 중단을 유발한다 — 토큰 자동 갱신과 헤더 전달이 필요하다.

data.go.kr 현재: Level 0 — 인증키를 URL 쿼리 파라미터(?serviceKey=)로 전달하고 수동 갱신만 가능. 서버 로그·브라우저 히스토리·Referrer로 키가 노출된다.

🇬🇧 API Key 방식은 명시적으로 지양하고 OAuth 2.0을 필수화(9개국 벤치마크: API Key 금지·OAuth 2.0 필수)🇦🇺 NAPIDS: 모든 API가 OAuth 2.0을 지원하도록 의무화(MUST)
레퍼런스
  • RFC 6749 — OAuth 2.0 (Client Credentials §4.4)
  • RFC 6750 — OAuth 2.0 Bearer Token Usage
  • MCP Specification 2025-11-25 (Authorization)
  • 한국 공공 API 개선 로드맵 §2.3/§3.2 API Key 헤더·OAuth 2.0 (gapi)

도구 네이티브 접근 (Tool-native Access)

에이전트는 API를 '도구(tool)'로 호출한다. MCP 서버나 함수 호출 스키마가 있으면 에이전트가 즉시 도구로 등록해 자연어로 데이터를 조회하지만, 없으면 개발자가 수동 래퍼를 만들어야 해 커버리지가 5% 미만에 머문다.

data.go.kr 현재: Level 1 — 비공식 커뮤니티 MCP/툴 래퍼가 일부 존재하나 유지·책임 주체가 불명확하고 부분 커버리지다.

데이터 제품화 (Data-as-a-Product)

에이전트가 신뢰하고 통합하려면 데이터가 '제품'처럼 다뤄져야 한다 — SDK·샘플코드·샌드박스·SLA·명확한 메타데이터가 있어야 에이전트 개발자가 빠르게 검증·연동하고 프로덕션에서 안정적으로 소비한다.

data.go.kr 현재: Level 1 — 샘플코드나 커뮤니티 SDK가 일부 있으나 공식 지원·샌드박스·SLA가 없다.

통합 정체성·카탈로그 (Unified Identity & Catalog)

에이전트가 여러 API를 조합하려면 단일 신원·단일 진입점이 필요하다. 전체 커버에 ID 130개가 필요한 파편화 구조에서는 에이전트가 수십 개 계정을 관리할 수 없어 실질적 자동화가 불가능하다.

data.go.kr 현재: Level 2 — 주요 포털이 단일 SSO/공통 키와 통합 API 카탈로그로 묶여 있고, 즉시 키 발급 등 가입이 간소하다.
